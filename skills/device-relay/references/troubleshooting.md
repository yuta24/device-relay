# Troubleshooting

| Symptom | Cause and fix | device-relay document |
| --- | --- | --- |
| `Failed to initialize for UI testing` (`Timed out while enabling automation mode.`) when starting | On a physical device, this is usually the device asking for its passcode while enabling automation mode, and timing out without it (UI Automation being off gives the same error). Ask the user to enter the passcode if the device shows that screen, then `relay start` again (the permission lasts a while, so starting right after tends to work). If `relay start` said `run relay runner install again` (relay 0.7.0 and earlier: `run relay install again`), confirm with the user and redo `relay runner install` first (relay rebuilds old builds by itself). If it still continues, ask them to check that Settings > Developer > Enable UI Automation is on. On a simulator it is usually temporary, so start again just once | docs/device.md, "UI オートメーションとパスコード" |
| `... timed out after 30 s` from `simctl`, `devicectl`, `xcrun`, or `security` | The tool did not answer in time and relay stopped it. Check that the command answers in a terminal, then try again | docs/sessions.md, "外部コマンドが応答しないとき" |
| "Untrusted Developer" on a physical device | Certificates such as a Personal Team's. Ask the user to trust it in Settings > General > VPN & Device Management, then start again | docs/device.md, "実機" |
| `relay doctor` shows locked (`passcodeRequired`), or operations have no effect | Ask the user to unlock the physical device | docs/setup.md, "環境の確認（relay doctor）" |
| `--allow-wifi` doesn't reach it | Ask the user to allow it in the "Local Network" permission dialog on the device | docs/device.md, "準備" |
| A physical device doesn't become `connected`, or the DDI isn't mounted | Ask the user to connect with USB and get it ready in Xcode's Devices and Simulators window | docs/device.md, "実機" |
| Signing or Team ID errors (physical device) | Ask the user to sign in to Xcode and create an Apple Development certificate. With several teams, `--team-id` | docs/device.md, "Team ID（実機の署名）" |
| `run relay runner install again to update the runner` appears (relay 0.7.0 and earlier: `run relay install again …`) | relay was updated after the runner was copied to `~/.relay/runner`. Ask the user to run `relay runner install` (`relay install` in 0.7.0 and earlier; it doesn't stop anything from working) | docs/setup.md, "Runner の用意（relay runner install）" |
| `unknown argument: '-target-arch-variant'` (building relay) | Another Swift comes first in PATH. `make install` uses `xcrun swift`, so use that | README, "Requirements" |
| One operation doesn't return for minutes, and busy continues meanwhile | A sheet from another process (Apple Account sign-in, for example) is up, and snapshots are stuck. Wait, or ask the user to close it | docs/elements.md, "待機（timeout）" |
| After an Xcode or iOS update, `touchSynthesis` in `relay health` became `xcui` and `foreground.source` became `fallback`, or elements' `hasKeyboardFocus` is `null` | Private APIs the runner uses became unavailable. It mostly keeps working through alternatives, so expect slower touches and name the target with `--bundle-id` | docs/private-api.md |
| `relay button home` has no effect on a physical device | On devices with a home button, the substitute swipe opens Control Center | docs/device.md, "ホームと音量ボタン" |
| `the OS refused the connection (Operation not permitted)` (exit code 3) | relay is inside the agent's sandbox and can't connect to localhost. The runner hasn't stopped. Ask the user for the settings in [Using relay from inside a sandbox](sandbox.md) | docs/sessions.md, "エージェントの sandbox から使う" |
| Exit code 3, but runner.json exists | `relay start` was killed and only the file remains (`relay status` shows `relay start not running` for the pid and no answer for ping). Clean up with `relay stop` (`not running`), then start | docs/sessions.md, "強制終了したとき" |
| The Mac is low on disk space, or a simulator's data is large | relay 0.7.0 and earlier let XCTest record the screen while the runner ran, and the videos can remain in the simulator, several GB per device (under `~/Library/Developer/CoreSimulator/Devices/<UDID>/data/Containers/Data/InternalDaemon/*/tmp/Attachments/`; relay never removes them). Other UI tests' attachments go there too, so don't delete anything yourself: tell the user the location and the document, and ask whether to remove them | docs/sessions.md, "以前の relay が残した画面録画" |
| `relay start --background` exits 1 with "a runner is already running" | The runner in `~/.relay/runner.json` answers on the same port. Check with `relay status` and use it as it is. Unless you started it yourself, don't stop it | docs/sessions.md, "バックグラウンドで動かす（relay start --background / status / stop）" |

Logs from a failed start are in `~/.relay/logs/` (`start-*.log`, `build-*.log`, `runner-*.log`). When `relay start --background` fails, it prints the cause, the end of the log, and the `start-*.log` path to stderr, so read that first, and if it isn't enough, read that file and the `build-*.log` / `runner-*.log` it mentions. `relay start` removes logs over 7 days old (keeping the newest 20 of each kind) and all but the newest 3 `.xcresult` per port, so copy what you need to keep out of `~/.relay`. What a running runner writes is never removed, and neither are your screenshots and recordings.
