# 既知の制約

現時点の device-relay の既知の制約です。全体の入口は [README](../README.ja.md) です。

- **非公開 API への依存**: タッチ合成の `private` 経路、前面アプリの取得、表示の向きの取得などは XCTest の非公開 API を使うので、Xcode / iOS の更新で使えなくなることがあります。消えた場合の多くは代わりの手段に切り替わりますが、シグネチャだけ変わった場合は検出できません。項目ごとの挙動は「[非公開 API の一覧](private-api.md)」を参照してください。
- **`xcui` 経路は遅い**: XCUI はタッチの前後に対象アプリのアイドル待ちをするため遅くなります（「[タッチ合成の経路](design.md#タッチ合成の経路)」）。
- **`/type`・`/key`**: 文字入力と特殊キーにはキーボードのフォーカスがある要素が必要です（「[文字入力と特殊キー](http-api.md#文字入力と特殊キー)」）。
- **`/health` の速さ**: 前面アプリを取得するぶん応答が遅くなります（「[画面サイズと速さ](http-api.md#エンドポイント)」）。
- **映像ストリームはまだない**: 画面はスクリーンショットのポーリングで取得します（シミュレータの縦向きで png 約 90 ms / jpeg 約 110 ms、横向きは正規化のぶん遅くなります）。縮小（`maxSize` / `scale`）しても、XCUI の撮影自体（約 60 ms）は変わりません。
- **ローカルネットワーク許可**: 実機では初回にローカルネットワークの許可ダイアログが出ることがあります。
- **システムの許可ダイアログと対象アプリ**: 許可ダイアログの表示中に後ろのアプリの要素を指定してタッチすると、何も送らずに止まります（「[システムの許可ダイアログ](elements.md#システムの許可ダイアログ)」）。
- **覆われていても止まらないタッチ**: 前面アプリの一覧が変わらない重なりや、出た直後のダイアログ・シートへのタッチは、成功を返しても届かないことがあります（「[別のアプリに覆われているとき](elements.md#別のアプリに覆われているとき)」）。
- **共有シートの中の要素**: 中身の形によっては画面上の位置が決まらず、要素指定のタッチを止めます（「[共有シートの中の要素](elements.md#共有シートの中の要素)」）。
- **待機中の前面アプリの切り替え**: 要素を待っている間に前面アプリが切り替わっても、対象アプリは変わりません（「[待機](elements.md#待機timeout)」）。
- **`/health` の画面サイズ**: 実機のランナー内の画面サイズは互換モードになるため、SpringBoard とスクリーンショットから求めます（「[画面サイズと速さ](http-api.md#エンドポイント)」）。
- **`portraitUpsideDown`**: 上下逆さを指定しても、アプリの表示の向きが変わらないことがあります（「[座標系と画面の向き](screen.md#座標系と画面の向き)」）。
- **音量ボタン**: `volumeUp` / `volumeDown` は実機でのみ使えます（シミュレータでは 400）。
- **実機の `home`**: 実機では `XCUIDevice.press(.home)` が成功を返すのに何も起きません（iOS 26.7.1 + Xcode 27 で確認）。testmanagerd が `Failed to load displays from CADisplay` で画面を取得できず、ボタンのイベントを画面に結びつかないキーボードから送るため、SpringBoard が無視します。そのため実機の `/button home` は、ホームインジケーターのジェスチャー（画面下端から上への素早いスワイプ）で代用します。`private` 経路では 0.12 秒のスワイプ（約 0.35 秒で応答）、`private` が使えない場合は XCUI のドラッグ（最初に 0.02 秒押す必要があります。約 1.8 秒）です。ホームボタンのない端末が前提で、ホームボタンのある端末では同じジェスチャーでコントロールセンターが開きます。シミュレータでは `press(.home)` が効くので、そのまま使います。
- **要素セレクタ**: 完全一致で要素を選びますが、隠れた要素やスナップショットの待ち時間には制約があります（「[要素セレクタ](elements.md#要素セレクタ)」）。
- **入っていないアプリの `/launch`**: 入っていないアプリの起動をランナーに送ると、XCTest がすぐには失敗せず長く busy になります（「[アプリの指定と起動](cli.md#アプリの指定と起動)」）。
- **automation mode の有効化でパスコードを求められる**: XCTest は、テストを始める前に端末の testmanagerd が automation mode を有効にするのを `XCUIApplicationStateTimeout`（既定 60 秒）だけ待ちます。このとき端末にパスコード入力画面が出ることがあり、入力されるまで有効化は終わりません（iOS 26.7.1 + Xcode 27 で、有効化に約 53 秒かかった回や、60 秒を超えて `Timed out while enabling automation mode.` で失敗した回がありました）。いったん許可されるとしばらくは有効なようで、直後に起動し直すと有効化は数 ms で終わります。入力の時間を取るため、スキームのテストアクションで `-XCUIApplicationStateTimeout 120` をランナーに渡し、ランナーは有効化が終わったら非公開関数 `_XCTSetApplicationStateTimeout` で 60 秒に戻します（`/launch` や `/terminate` の待ち時間は変わりません。関数がなければ 120 秒のままです。`relay launch` / `terminate` は、どちらのランナーでも切らないよう 30 + 120 秒まで応答を待ちます）。120 秒以内に入力されなければ時間切れになるので、端末でパスコードを入力してから `relay start` し直してください。スキームは Runner のソースのハッシュに含まれるので、この引数のない古いビルドは `relay start` が自動で作り直します（docs/setup.md の「ランナーの版」）。`relay install` で入れた Runner（`~/.relay/runner`）はコピーの時点のソースなので、コピーが古ければ `relay start` が知らせるとおり `relay install` をやり直してください。起動に失敗したときの hint は、実機の UI テスト初期化の失敗（`Failed to initialize for UI testing`）ならパスコードの入力、UI オートメーションの設定、ロック解除の順に、シミュレータでの同じ失敗なら「1 回だけ起動し直す」を表示します。`** TEST FAILED **` などテストの失敗では hint は出さず、ランナーのログのパスだけを示します。
- **表示が複数ある端末（iPhone Duo）**: 前面アプリが載っている表示に合わせて動きますが、表示の判定やタッチ・向きには制約があります（「[表示が複数ある端末](screen.md#表示が複数ある端末iphone-duo)」）。
- **iPad のウィンドウ表示**: 画面上の位置を決められないウィンドウでは、要素指定のタッチを止めます（「[iPad のウィンドウ表示](screen.md#ipad-のウィンドウ表示)」）。
- **シミュレータのランナーには Mac の外から届かない**: シミュレータのランナーは `127.0.0.1` だけで待ち受けます。Mac の LAN 側のアドレスで待ち受けていた以前のビルドと違い、ほかのマシンから直接は接続できません（relay はシミュレータに `127.0.0.1` で接続するので、relay からの操作は変わりません）。
- **シミュレータの自動用意はしない**: セッションごとにシミュレータを複製・作成することはしません。並列に動かす台数のシミュレータは利用者が用意し、`--udid` / `--device` で分けます。同じ機種名が OS ごとにあるので、同じ OS で並列に動かすときは `--os` か `--udid` で区別します。`relay start` が boot したシミュレータは、その `relay start` の終了時に shutdown します。
- **セッションのポートの予約**: `8101`〜`8199` は `relay start` どうしでしか予約されません。空きを確かめてからランナーが待ち受けるまでの間（ビルドを含みます）に、ほかのプロセスが同じポートを使うと、`relay start` は失敗します。そのときは起動し直すか、`--port` で指定してください。
- **セッションと強制終了**: `relay start` を `kill -9` などで強制終了すると、ロックは外れますが、xcodebuild とランナーが残ることがあります。runner.json のランナーが応答していれば同じセッションの起動はエラーになるので `relay stop --session <名前>` で止めてください。別のセッションからその端末を使う場合は検出できません。
- **外部コマンドが応答しないとき**: `simctl`・`devicectl`・`xcrun`・`security` などは時間を区切って呼ぶので、応答がなければ relay は止まったままにならず、`xcrun simctl list devices --json timed out after 30 s` のようなエラーになります（問い合わせは 30 秒、`devicectl` は 60 秒、`simctl boot` は 5 分、`bootstatus` は 10 分、`shutdown` は 2 分。終了コードはほかの失敗と同じで、`relay doctor` は ✗ や `!` を出して先に進みます）。ビルドとランナーの実行には制限がありません。
- **usbmux 非対応**: 実機への接続には CoreDevice トンネル（または `--allow-wifi` で Wi-Fi）が必要です。
- **通信は平文**: 認証はトークンだけで、TLS はありません（「[認証](http-api.md#認証)」の脅威モデルを参照）。`relay` を `kill -9` などで強制終了した場合は `~/.relay/runner.json` が残ります（サブコマンドは接続できずに終了コード 3、別のランナーが同じポートにいれば 4 になります）。カレントディレクトリや親の `.relay/runner.json` は読まないので、以前の版が残したファイルが原因の 401 は起きません（手で置いたファイルは `--runner` で使います）。
